# Recovery attempt selection in context-record reads

The context-record reader accepted a server-validated recovery descriptor but discarded it, then rebuilt the ordinary source job ID and rejected the original quarantined job as inactive. Its attempt digest also used ordinary-only lineage. An actual controlled recovery failed at this boundary before generator execution; the original hold code and exact attempt scope were recovered from retained content-free diagnostics. A later post-terminal source rejection was separate and is not treated as the cause.

This one-file candidate selects a recovery job only from the existing server-authenticated callback descriptor, verifies the same owner/source/client/transcript and active lease/fence/graph, and uses the existing admission-lineage helper in the attempt digest. Ordinary jobs retain their original selection and digest. Request bodies gain no job-selection authority; endpoint schemas and ownership checks are unchanged.

Eight targeted offline cases passed in both author and independent review. They invoke the actual production dependency factory, real callback/graph/recovery code over serialized fake Firestore, reproduce the baseline failure, and cover the corrected path, worker context, ordinary behavior and invalid scope/lease/source/consent. No positive-path callback override substitutes for the selection being tested. These are not real database/model or service-interpreter results. The frozen fixtures depend on the existing recovery test package and retain workspace-relative paths; `.py.source` preserves reviewed bytes and is not an activated deployment.

The first controlled successor is closed and remains quarantined. Its resource reservation was independently qualified and settled without modifying the failed job, source, tombstone or retained effects. This fix does not replay it or authorize another generation. Actual import/deployment qualification and any subsequent controlled execution must be reported separately.
