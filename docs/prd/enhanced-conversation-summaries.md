## 1. Problem

OMI's built-in conversation summaries are generated by a generic LLM call that has no knowledge of the user beyond the current transcript. The Ella summary adapter (legacy n8n → Letta flow) attempted to improve this but is outdated and disconnected from the current agent system (OpenClaw).

The result: summaries like *"Discussed knee pain and morning routine"* instead of *"Third mention of left knee issue this month (first reported Jan 15). Escalation pattern — consider scheduling PT. Connected to hiking goal timeline."*

OpenClaw agents have deep user context via ClawVault long-term memory, cross-conversation patterns, health history, and relationship graphs. This context should enhance summaries post-processing.

## 2. Goals

1. **Enhance conversation summaries** with OpenClaw's deep user knowledge — without replacing OMI's built-in processing pipeline (dedup, action items, events, semantic search)
2. **Add MCP write capability** for conversation structured data — a missing feature that's a logical upgrade to the existing read-only MCP tools
3. **Notify OpenClaw of new conversations** via lightweight ID-only webhook — avoiding transcript bloat in agent context
4. **Minimize diff with upstream BasedHardware/omi** — all changes should be modular, self-contained, and easy to maintain across upstream pulls

## 3. Non-Goals

- Replacing OMI's built-in conversation processing pipeline
- Real-time summary generation during conversation (enhancement is post-process)
- Modifying the iOS app for this feature
- Changing the Ella summary adapter (legacy n8n flow) — it can remain as-is or be disabled separately

## 4. Architecture

### Flow

```
OMI conversation completes
    |
    +-- Normal pipeline runs (built-in LLM: title, overview, dedup,
    |   action items, events, category, apps)
    |
    +-- Saved to Firestore with standard structured data
    |
    +-- [NEW] Ella post-save hook fires:
    |   POST to n8n with { conversation_id, uid, timestamp }
    |   (lightweight — no transcript, no structured data)
    |
    +-- n8n workflow receives notification:
    |   - Looks up uid → OpenClaw agent mapping (Postgres dashboard DB)
    |   - Forwards to OpenClaw agent API as system event:
    |     "Conversation {id} ready for enhancement"
    |
    +-- OpenClaw agent (main session) processes:
        1. Tool: mcporter call omi.get_conversation_by_id conversation_id=X
           (retrieves transcript + existing structured data)
        2. Tool: clawvault search "relevant context for this conversation"
           (user health patterns, projects, relationships, recent themes)
        3. Agent generates enhanced summary with deep user knowledge
        4. Tool: mcporter call omi.update_conversation_summary
           conversation_id=X overview="Enhanced summary..."
           (writes back to Firestore)
        5. All tool results pruned naturally by context GC
```

### Why This Design

| Decision | Rationale |
|----------|-----------|
| Post-process (not pipeline replacement) | Preserves OMI's dedup, action items, events, semantic search |
| ID-only notification (not full transcript) | Prevents agent context bloat; transcripts can be 10K+ tokens |
| Agent-side retrieval via MCP tool | Tool results are transient — GC prunes them naturally |
| Main agent session (not dedicated) | Main agent has full day's context, mood, recent conversations |
| n8n as intermediary | Handles uid→agent mapping, auth, retry logic; Ella dev team owns n8n |
| Ella post-save hook (not per-user webhook) | Server-side, automatic for all users, no per-user config needed |

### Why Not Per-User Webhook

OMI's developer webhook system is strictly per-user (stored in Redis, configured via Developer Settings in the iOS app). There is no global default. Options:

- **Per-user Redis injection**: Fragile, lost on Redis flush, per-user maintenance
- **iOS app hardcoded**: Couples iOS app to this feature
- **Ella server-side hook**: Fires for ALL conversations automatically, no per-user config, clean separation

**Decision**: Ella server-side hook. Modular, lives in `backend/ella/`, doesn't touch upstream code.

## 5. Backend Changes

### 5.1 MCP Write Tool — `update_conversation_summary`

**File**: `/root/omi/backend/routers/mcp_sse.py`
**Type**: New tool added to existing MCP SSE handler
**Diff impact**: Additive only — new tool registration + handler function

Add a new MCP tool to the existing SSE tools list:

```python
{
    "name": "update_conversation_summary",
    "description": "Update the structured summary fields of an existing conversation (title, overview, emoji, category)",
    "inputSchema": {
        "type": "object",
        "properties": {
            "conversation_id": {"type": "string", "description": "The conversation ID to update"},
            "title": {"type": "string", "description": "New title (optional)"},
            "overview": {"type": "string", "description": "New summary/overview text (optional)"},
            "emoji": {"type": "string", "description": "New emoji (optional)"},
            "category": {"type": "string", "description": "New category (optional)"}
        },
        "required": ["conversation_id"]
    }
}
```

Handler calls `conversations_db.update_conversation(uid, conversation_id, update_data)` which already exists and accepts arbitrary fields via Firestore `doc_ref.update()`.

**Scope**: ~40 lines of code. Self-contained in the MCP router. No modifications to existing tools or handlers.

**Testing**: `mcporter call omi.update_conversation_summary conversation_id=TEST overview="test"` then verify via `mcporter call omi.get_conversation_by_id conversation_id=TEST`.

### 5.2 Ella Post-Save Notification Hook

**File**: `/root/omi/backend/ella/hooks/conversation_completed.py` (new file)
**Registration**: `/root/omi/backend/ella/__init__.py`
**Diff impact**: New file in ella/ directory + one registration line

This is a lightweight hook that fires after `conversations_db.upsert_conversation()` in the processing pipeline. It POSTs only the conversation ID and user ID to a configurable n8n webhook.

```python
# ella/hooks/conversation_completed.py

import os
import requests
import threading
import logging

logger = logging.getLogger(__name__)

CONVERSATION_READY_WEBHOOK = os.getenv(
    'ELLA_CONVERSATION_READY_WEBHOOK',
    'https://n8n.ella-ai-care.com/webhook/conversation-ready'
)

def notify_conversation_ready(uid: str, conversation_id: str):
    """
    Lightweight notification that a conversation has been processed
    and saved. Sends only IDs — no transcript, no structured data.
    The receiving agent retrieves what it needs via MCP tools.
    """
    if not CONVERSATION_READY_WEBHOOK:
        return

    def _send():
        try:
            requests.post(
                CONVERSATION_READY_WEBHOOK,
                json={
                    "uid": uid,
                    "conversation_id": conversation_id,
                    "event": "conversation_ready"
                },
                timeout=5
            )
        except Exception as e:
            logger.warning(f"conversation-ready webhook failed: {e}")

    threading.Thread(target=_send, daemon=True).start()
```

**Integration point**: Called from `process_conversation()` after the Firestore save (line ~688), inside the existing Ella extension pattern. Could be registered as an adapter/hook via `ella/__init__.py` or called directly.

**Alternative integration** (if we want zero changes to `process_conversation.py`): Register as a post-save callback in the Ella adapter system, similar to how the summary adapter intercepts the summary step.

### 5.3 Environment Variable

Add to `/root/omi/backend/.env`:
```
ELLA_CONVERSATION_READY_WEBHOOK=https://n8n.ella-ai-care.com/webhook/conversation-ready
```

## 6. n8n Workflow (Ella Dev Team)

**Owner**: Ella dev team member (has n8n keys, Postgres DB access)

### Workflow: `conversation-ready`

1. **Trigger**: Webhook node at `/webhook/conversation-ready`
2. **Input**: `{ conversation_id, uid, event: "conversation_ready" }`
3. **Lookup**: Query Postgres dashboard DB to map `uid` → OpenClaw agent ID / session
4. **Forward**: Call OpenClaw agent API with system event:
   ```json
   {
     "message": "New OMI conversation ready for enhanced summarization. Conversation ID: {conversation_id}. Retrieve via mcporter, enhance with your deep knowledge of the user, and write back the improved summary.",
     "conversation_id": "{conversation_id}",
     "uid": "{uid}"
   }
   ```
5. **Error handling**: Log failures, retry once, send Telegram notification on persistent failure

### Dependencies

- n8n admin access (Ella dev team)
- Postgres dashboard DB schema for uid → agent mapping
- OpenClaw agent API endpoint and auth

## 7. OpenClaw Agent Integration

**Owner**: Fleet engineering (Claude Code / OpenClaw config)

The OpenClaw main agent receives the system event and processes it using existing tools:

1. `mcporter call omi.get_conversation_by_id conversation_id=X` — Retrieves full conversation
2. `clawvault search "relevant context"` — Searches long-term memory for related patterns
3. Agent generates enhanced summary using both inputs
4. `mcporter call omi.update_conversation_summary conversation_id=X overview="..."` — Writes back

This requires no new OpenClaw skills or code — just the system event routing from n8n and the MCP write tool being available.

### Context Management

- Tool call results (transcript, ClawVault results) are transient — OpenClaw's compaction/GC prunes them naturally
- Main agent session is used (not dedicated) — agent has full day's context for maximum enrichment quality
- If conversations arrive in rapid succession, they queue as system events and process sequentially

## 10. Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Upstream OMI merge conflicts | Merge difficulty | All changes in `ella/` directory or additive-only to existing files |
| n8n webhook down | Conversations not enhanced | Standard summaries still work (enhancement is additive) |
| OpenClaw agent overloaded | Delayed enhancement | System events queue naturally; non-blocking |
| Enhanced summary worse than original | Poor UX | Phase 5 quality tuning; can disable hook via env var |
| Rate limiting on MCP calls | Failed enhancements | mcporter retries; n8n retry logic |

## 11. Success Metrics

- Enhanced summaries reference user-specific context (health patterns, project names, relationship context) that generic summaries miss
- Enhancement latency < 60 seconds from conversation completion
- Zero impact on OMI's built-in processing pipeline performance
- Clean upstream merge with < 5 lines of diff outside `ella/` directory
